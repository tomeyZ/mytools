## JSON 美化工具：启用 jsoneditor tree 模式（方案 A）

**背景**：用户反馈 mytools 的 JSON 美化功能无法像 bejson.com 那样折叠/展开节点。

**排查结论**：
- 实际使用的是 `jsoneditor` 库（底层 code 模式才是 ace，非纯 ace）
- 原配置 `mode: 'code'` 锁死在纯文本模式，ace 不感知 JSON 结构，故无折叠能力
- `JsonFormatBak.vue`（旧备份）用的是 `vue-json-pretty`，该组件本身支持折叠（`:deep` 控制默认层级）
- 顺带发现 bug：`onModeChange` 里配置 `aceEditor.maxLines` 在初始模式下不触发，需初始化后手动补调

**改动**（`frontend/src/components/JsonFormat.vue`）：
- 默认 `mode: 'tree'`，`modes` 收窄为 `['tree', 'code']`（去掉 form/text/view）
- 工具条新增「树视图 / 代码视图」切换按钮组（active 高亮 + 分隔线），配套 `currentMode` ref + `switchMode()`（try-catch 包裹 setMode）
- 抽出 `applyAceOptions()`，在 `onModeChange` 与初始化后各调一次，修复原失效的 ace 配置
- `.jsoneditor` 补 `min-height: 0`（flex 子项默认 min-height:auto 会撑破外层滚动）

**验证**：`npm run build`（managed node 22.22.2-2 的 npm.cmd）通过，46 modules transformed，仅原有的 chunk 体积警告。

**待确认**：tree 模式下粘贴大段非法 JSON 的报错体验，需用户实际试用反馈。

## JSON 美化滚动问题修复（maxLines: Infinity 反模式）

**用户反馈**：代码视图下 JSON 内容很长但无法滚动看到下面数据。

**根因**：上一版我加的 `aceEditor.setOptions({ maxLines: Infinity })` 是错的——
- JSONEditor 给 ace 容器固定高度（CSS `height: 100%`），ace 无法撑破
- `maxLines: Infinity` 想让 ace 按内容撑开高度，但被外层 `overflow:hidden` 截掉
- 结果：ace 以为可滚、外层以为没东西可滚 → 彻底看不到下面

**修复**（`frontend/src/components/JsonFormat.vue`）：
- 删除整个 `applyAceOptions()` 函数、`maxLines: Infinity` 配置、初始化后补调、onModeChange 里的 ace 配置分支——这套机制本来就是为错误的初衷服务的，整套清掉
- `onModeChange` 现在只剩 `currentMode.value = newMode`，同步视图切换按钮高亮
- `.jsoneditor` 加 `overflow: auto` 兜底（正常情况 JSONEditor 内部会处理滚动，外层滚动条不出现）

**教训**：JSONEditor 这种"自带 DOM 结构"的库，不要轻易改它的子节点属性（ace 配置、maxLines 等）。库的默认行为经过了大量兼容性测试，外层 flex + overflow 就够用了。

**验证**：`npm run build` 通过，46 modules transformed。

## JSONEditor 底部白条根因：has-status-bar 的 padding-bottom

**用户反馈**：滚动到最底部后，JSON 内容下方有一条约 26px 的白条（红圈圈出）。

**根因排查**：
- 不是 ace 内部的事（之前被 `maxLines: Infinity` 误导过一次）
- 查 `node_modules/jsoneditor/dist/jsoneditor.css:846-849` 找到：
  ```css
  div.jsoneditor-outer.has-status-bar {
    margin-bottom: -26px;
    padding-bottom: 26px;  /* ← 白条来源 */
  }
  ```
- 查 `node_modules/jsoneditor/dist/jsoneditor.js:2980-2981`，初始化时根据 `options.statusBar` 给 outer 加 `has-status-bar` 类
- 原有代码用 `display: none` 隐藏 statusbar 节点，但 `has-status-bar` 类没被移除 → padding-bottom 仍生效 → 26px 空白

**修复**（`frontend/src/components\JsonFormat.vue`）：
- options 加 `statusBar: false`：JSONEditor 不创建 statusbar、不加 `has-status-bar` 类，从源头解决
- 删除全局 style 里的 `.jsoneditor-statusbar { display: none !important }` —— 节点根本不存在，CSS 失效成死代码

**验证**：`npm run build` 通过。

**教训（升级）**：不要用 CSS `display: none` 去掩盖库自己生成的功能节点。要查库的 options API，找根因开关。这次发现的另一个例子：上次用 `maxLines: Infinity` 改 ace 内部行为也踩坑了——**库对子节点的行为是经过设计的，外层 flex + overflow 控制就行**。

## JSONEditor 底部白条第二层根因：ace onChangeHeight 内联样式 + frame 缺 overflow:hidden

**用户反馈**：上一轮加了 `statusBar: false` 后刷新页面，白条**还在**，形态变了（底部更大一片）。

**根因排查（第二层）**：
- `statusBar: false` 只阻止了初始化时加 `has-status-bar` 类，但还有一个持续运行的机制没关掉
- 查 `node_modules/jsoneditor/dist/jsoneditor.js:2971-2977` 的 `onChangeHeight` 回调（注册在 ace 上，content 变化就触发）：
  ```js
  onChangeHeight: function onChangeHeight(height) {
    var statusBarHeight = me.dom.statusBar ? me.dom.statusBar.clientHeight : 0;
    var totalHeight = height + statusBarHeight + 1;
    me.content.style.marginBottom = -totalHeight + 'px';
    me.content.style.paddingBottom = totalHeight + 'px';   // ← JS 内联样式，优先级 1000
  }
  ```
- 即使 statusBarHeight=0，totalHeight = ace 内容高度 + 1（巨大数字）
- JSONEditor frame CSS（`.jsoneditor`）默认 **没有 overflow:hidden** + position:relative
- 结果：outer 被 JS 持续撑高 → 溢出 frame → 直接渲染成白条

**修复**（`frontend/src/components/JsonFormat.vue`，在第一层基础上叠加）：
- frame 加 `overflow: hidden`：裁掉外溢部分（兜底）
- 新增 `.jsoneditor-outer { padding-bottom:0 !important; margin-bottom:0 !important }`：从源头阻止撑高
- `!important` 永远胜过内联样式（CSS 优先级规则），即使 onChangeHeight 持续触发也无效

**验证**：`npm run build` 通过。

**教训（再升级）**：
1. 库对外 options 是好事，但内部回调（如 onChangeHeight）可能绕过 options 持续修改 DOM——只查 init 阶段不够，必须 grep 回调函数 / 动态赋值（`grep -n "this.content.style"`）
2. 库基础 CSS 有结构性 bug（frame 缺 overflow:hidden）时，外部 `!important` 是最直接的修法，不必 fork 库
3. Wails 桌面应用改前端代码后需要重新构建/刷新才能看到效果（不像纯 Web 浏览器自动 HMR），如果用户说"还是这样"先确认是否刷新过

**三次踩坑的最终结论（JSONEditor 集成）**：
- ❌ 不要用 `display: none` 掩盖库节点，要找 options 关闭
- ❌ 不要改库子节点属性（ace maxLines 等），库默认行为经过兼容性测试
- ❌ 不要相信 init 时 CSS 是稳定的，库有回调会动态改内联样式
- ✅ 外层 flex + overflow 控制布局
- ✅ 需要覆盖 JS 内联样式时用 `!important`
- ✅ 排查库行为要 grep 完整生命周期（init + 回调）

## 第四次修正：CSS 优先级冲突 + ace 容器无高度（关键事实）

**用户反馈**：第三轮修复后白条**仍在**。用户主动质疑"这块也用到 ace 了吗"——推动我停止猜测、去查真实 DOM。

**关键事实 1：ace 容器没有明确高度**
- `node_modules/jsoneditor/dist/jsoneditor.js:2896`：
  ```js
  this.editorDom.style.width = '100%'; // TODO: move to css
  this.content.appendChild(this.editorDom);
  var aceEditor = _ace.edit(this.editorDom);
  ```
- **JSONEditor 只给 ace 容器设了 width，没设 height**
- 后果：ace 按内容行数撑开高度（58 行 JSON ≈ 1160px），直接撑破 outer（outer 高度 = frame 高度）
- **因此 frame 必须 `overflow: auto`**，用 hidden 会裁掉内容（复现第一次"滚动失效"的 bug）

**关键事实 2：scoped vs global CSS 优先级冲突**
- 构建产物实测（`grep -o "\.jsoneditor\[data-v-[a-z0-9]*\]{[^}]*}" dist/assets/*.css`）：
  - `.jsoneditor[data-v-8a3a1375]{flex:1;width:100%;min-height:0;overflow:auto}` → 优先级 **(0,2,0)**
  - `div.jsoneditor{border:...;overflow:hidden}` → 优先级 **(0,1,1)**
- **(0,2,0) > (0,1,1)：scoped 的 `overflow: auto` 胜出，全局块的 `hidden` 被静默覆盖**
- 我在第三轮加的 `overflow: hidden` 兜底**根本没生效**，这是第二次在同一处犯错

**关键事实 3：ace 自身不是白条来源**
- `node_modules/ace-builds/css/ace.css:67-78`：`.ace_scroller` 是 `position:absolute; top:0; bottom:0`，**没有 padding-bottom**
- 推翻了第三轮"ace 虚拟滚动 padding"的假设

**本轮修复**（`frontend/src/components/JsonFormat.vue`）：
- frame 的 `overflow: auto` **保留**（撑破 outer 时必须能滚）
- 删除全局块 `div.jsoneditor` 里的 `overflow: hidden`（写了也不生效，纯误导），改为注释说明优先级陷阱
- scoped 块 `.jsoneditor` 注释补充：overflow 只能在这里控制

**新增诊断工具**：`frontend/debug-jsoneditor.js`
- 在 Wails DevTools Console 里粘贴运行，输出：当前模式、各层元素高度/内联 padding/计算后 padding/overflow、底部命中测试（白条是什么元素）、frame 与 outer 的滚动信息
- 用法：`wails dev` 或 `wails build -debug` → 右键 Inspect → Console 粘贴

**方法论教训（最重要）**：连续 4 次"你试试看"都失败，说明**纯代码推理已经不够**——CSS 布局问题必须拿真实 DOM 的计算样式才能定位。以后遇到此类问题应**尽早引入实测**（浏览器 DevTools / 诊断脚本 / agent-browser），而不是反复推理改代码让用户试。

**agent-browser 环境备注**：本机未安装 agent-browser，装它需要下载 ~500MB Chromium。轻量替代：写诊断脚本让用户在 DevTools 里跑。

**用户回传诊断脚本输出（决定性数据）**：
```

outer      (.jsoneditor-outer) 高度 339px, 内联paddingBottom 1px

tree       (.jsoneditor-tree) 不存在  → 实测时处于 code 模式
```

**算出来的真凶**：`339 - 304 = 35`，精确命中 CSS `jsoneditor.css:851-854`

```css
div.jsoneditor-outer.has-main-menu-bar { margin-top: -35px; padding-top: 35px; }
```

frame 内容区 340，outer 只到 304 → **底部 36px 真空 = 白条**。
负 margin 本意是"上提盖住 35px 高的菜单栏"，而我用 `display:none` 藏了菜单栏 → 没东西可盖 → 整个 outer 被凭空上提 35px。

### 订正：前几轮笔记中的三处错误（以本轮为准）

1. **❌「JSONEditor 只给 ace 容器设 width 没设 height」→ 错**
   `jsoneditor.js:2895-2896` 两行都设了：
   ```js
   this.editorDom.style.height = '100%';
   this.editorDom.style.width = '100%';
   ```
   ace 容器是 100% 高度 → ace 内部滚动，**不是**按内容行数撑开。因此 frame 的 `overflow:auto` 只是无害兜底，不是必需。

2. **❌「onChangeHeight 是 ace 的回调」→ 错，它是 ErrorTable 的**
   `jsoneditor.js:2954-2978`：该回调传给 `new ErrorTable({...})`，只在校验错误出现时按错误表高度调整 outer。
   正常情况（无错误）只设 `paddingBottom = 0+0+1 = 1px`——与诊断输出完全吻合。

3. **❌ `.jsoneditor-outer { padding-bottom:0 !important; margin-bottom:0 !important }` → 有害，已删**
   这个负 margin + padding 组合是**给错误表格腾位置的正常机制**：
   - 错误表格 `.jsoneditor-validation-errors-container` 是 frame 里 outer 的**兄弟节点**（`jsoneditor.js:2979`），普通流布局
   - outer 设 `padding-bottom: N; margin-bottom: -N` → 内容区收缩 N，错误表格被上提 N 落入空出来的位置
   - 我强行归零后，错误表格会掉到 outer 下方撑出 frame
   - 注：`showErrorTable` 默认 `['text','preview']`（`jsoneditor.js:2692`），本项目只用 tree/code 模式所以没暴露，但属于埋雷

**四条经验（本轮最终版）**：
- ✅ 库有 options 就用 options 关功能，**不要用 CSS 掩盖库节点**（菜单栏/状态栏都栽在这）
- ✅ 排查 CSS 布局：**先拿真实计算值再推理**。四轮纯代码推理全错，一份 `getComputedStyle` 输出一次命中
- ✅ 加 `!important` 覆盖库的内联样式前，**先确认那段内联样式的用途**——可能是库的正常布局机制（错误表格那次差点埋雷）
- ✅ 用户回传的数据要"算"不要"看"：`339-304=35` 精确对上 CSS 里的 `-35px`，这种数字吻合就是铁证

## 去转义函数重写（行为对齐 bejson）

**用户反馈**：用同样的转义 JSON 粘 bejson 能解析，自己的工具说"未检测到转义"或显示"没变化"。

**原 bug**：剥完一层后只要能解析成合法 JSON 对象就 stringify 一遍——这一遍又把字符串值里的真实换行/字符重新转义回去。视觉上"什么都没改"，用户自然以为没成功。

**重写后的去转义函数**（`frontend/src/components/JsonFormat.vue`）：
- 路径 A：循环 `JSON.parse`，剥到不能再剥为止；按最终类型分三种展示
  - 结构化 JSON → `JSON.stringify(obj, null, 2)` 格式化展示
  - 单字符串 → `editor.setText(parsed)` 原样展示（保留真实换行/字符，不二次转义）
  - number/null/boolean → `String(final)` 字面化
- 路径 B：路径 A 的 `current` 仍非合法 JSON（典型如从日志/SQL/curl 复制来的 `\"foo\":\"bar\"` 半成品），按字面解码
  - 顺序固定：`\\\\` → 占位符 → `\"` → `"` → `\n` → newline → `\t` → `\r` → 占位符 → `\`（防止反转义冲突）
- 真正的"无可去除"才用 error.value 报错：之前会在 toolbar 右侧出竖排"未检测到转义…"——已彻底移除该 UI，错误统一走底部 error 条

**顺便清理**：
- 删除 `.unescape-info` span、CSS、ref 声明、return 字段
- 6 个按钮（格式化/压缩/排序/转义/Unicode）原本都用 `unescapeInfo.value = "已格式化"` 这样的成功提示，全部移除——成功改为静默（编辑器自己会变化即反馈），失败用 `error.value`

## 空内容切换视图报错（JSONEditor 空状态的两个坑）

**用户反馈**：编辑器没有任何内容时点「树视图」，报
`切换视图失败：Parse error on line 1: ^ Expecting 'STRING', 'NUMBER', ... got 'EOF'`

**根因 1（code → tree）**：`setMode` 内部会取当前模式的数据再喂给新模式
（`jsoneditor.js:1576-1585`）：
```js
var asText = config.data === 'text';        // tree=false, code=true
var data = this[asText ? 'getText' : 'get']();
...
this[asText ? 'setText' : 'set'](data);
```
切到 tree 时 `get()` → `textmode.get = parse(getText())`（`jsoneditor.js:3386`）→ `parse('')` 抛 EOF。

**根因 2（tree → code，顺带发现的隐藏 bug）**：
`treemode.getText = JSON.stringify(this.get())`（`jsoneditor.js:18288`），
内容为空时 `get()` 返回 undefined → **`JSON.stringify(undefined) === undefined`**，
`getText()` 返回的是 undefined 而不是 `''`。
本项目所有按钮都写 `editor.getText().trim()` —— 空内容点格式化/压缩/排序/转义等
会直接抛 TypeError（未捕获，UI 无任何反馈，按钮静默失效）。

**修复**（`frontend/src/components/JsonFormat.vue`）：
- 新增 `getEditorText()`：`String((editor && editor.getText()) ?? '')`，收敛空值；6 处 `getText()` 全部改用它
- `switchMode()` 开头 `error.value = ''` 清掉上次残留的错误
- 切换前若内容为空统一 `editor.setText('{}')` 占位（两个方向都需要）
- 切 tree 失败的提示改为中文可读文案，不再直接抛 jison 原始错误

**教训**：第三方库"空状态"的返回值类型要实测或查源码确认——
`JSON.stringify(undefined)` 返回 `undefined` 而不是字符串，容易漏。
凡是库 API 返回值直接调字符串方法的，先归一化类型。

## 去转义最终版：四分支策略 + GUARD 占位符（对照用户真实数据回归通过）

**用户实测暴露的第二轮 bug**：输入是**无外层引号的裸转义文本**（`{\"BigId\":...}` 开头），
旧路径 B 把 `\n` 也解码成真实换行 → `longDescription` 里的 `\n` 撕裂 JSON → 输出非法。

**关键认知**：`\n` 在 JSON 字符串内部是**合法转义序列（语法的一部分）**，绝不能解码；
只有当整体不是 JSON（纯文本场景）时才该解码。同一个 `\n`，场景不同处理相反。

**最终实现**（`unescapeAndFormat`，配合 `guardControls`/`unguardControls`/`tryParse`/`fullUnescape` 辅助函数）：
1. **GUARD 技巧**：剥层前把 `\n`→`\u0000A` 等控制序列用 PUA 私有区字符占位，
   防止剥层过程中 `\n` 提前变成真实换行污染 JSON；最终输出前再还原
2. 剥层循环：先整体 `JSON.parse`；失败且含 `\"` 时补一层引号当字符串内容再 parse（限含 `\"` 才走，否则纯文本原地打转）
3. 四分支展示：
   - ① 剥层后是结构化 JSON → 格式化输出
   - ② 是单字符串 → 原样展示（不二次转义）
   - ③ "像 JSON 但语法残缺"（如用户贴丢了末尾 `}`）→ 只还原 `\"`→`"`，**保留 `\n`**，报错提示检查括号
   - ④ 纯文本 → 完整反转义（`\n`/`\t`/`\uXXXX` 全解码）
4. ③④ 的判定依据：剥层结果**不含** `{"` 或 `":` 这类 JSON 结构特征 → 纯文本；含 → 残缺 JSON

**回归验证**（8 case 全过，脚本已删）：用户原始输入（缺 `}`）走③无污染；
补全后走①输出合法 JSON；带引号转义/双层转义/合法 JSON/纯文本/半成品/干净单串全部符合预期。

**发现用户的输入本身缺 1 个 `}`**：括号计数 depth=1（用"字符串外统计"算法：跳过转义字符和字符串内的括号）。
"去转义结果不对"有一半原因是输入本身残缺——但工具的职责是**不把残缺内容进一步搞坏**，③分支就是干这个的。

**方法论**：
- 验证脚本必须读**用户原始数据文件**（`fs.readFileSync`），手工复制进 JS 字符串字面量会引入二次转义错误，之前两轮假阳性都是这么来的
- `.js` 文件在 `"type":"module"` 的 package 里默认按 ESM 解析，验证脚本要用 `.cjs`
- 字符串处理逻辑：写独立脚本跑 case 表回归，别在组件里改完就交付

## 转义按钮改为 bejson 同款「裸转义」形态 + 保护符位置感知化

**用户反馈**：点「转义」后整个 JSON 被包上外层引号（`"{\"BigId\":...}"`），质疑为什么。

**原因**：旧实现 `JSON.stringify(整个文本)`——产出完整 JSON 字符串字面量，外层引号是形态的一部分，用于塞进另一个 JSON 的字符串字段。但用户数据流（日志/SQL 复制）用的是**裸转义形态** `{\"a\":1}`（无外层引号）。

**修复 1**：`escapeJson` 改为 `JSON.stringify(text).slice(1, -1)`——剥掉首尾引号输出裸形态。连点叠加多层仍正确（每次 stringify 都在当前文本上转义）；「去转义」的补引号路径可对称还原。

**修复 2（连带发现的深层 bug）**：GUARD 保护符原是无差别正则替换，把所有 `\n` 都扣成字面量——导致「格式化 JSON（真实换行）→ 转义 → 去转义」回不去（格式换行全变 `\n` 字面量卡在字符串外，JSON 非法）。

核心认知——**同一个 `\n` 在两种文法里含义相反**：
- 转义文法（stringify 产物）：值内换行是 `\\n`（3字符），格式化换行是 `\n`（2字符、**字符串区域外**）→ 该还原成真实换行
- 残缺文法（日志手抄）：值内换行就是 `\n`（2字符、**字符串区域内**）→ 必须保持字面量，还原会撕裂 JSON

区分手段是**位置**：`guardControls` 从正则替换改为逐对扫描 + 字符串区域跟踪：
- `\\` 成对消费（不能从中间截断，否则 `\\n` 被拆坏）
- `\"` 视为转义后的字符串定界符，切换 inString 状态
- 仅 `inString` 时的 `\n \t \r \b \f` 换 GUARD；区域外的原样保留交给 JSON.parse 还原

**回归**：21 case 全过（紧凑/格式化/复合/多层/纯文本/带引号旧形态/残缺文法/合法JSON/用户数据缩影，含 BigId 大数无损、值内换行语义）。

**附带说明**：用户转义输出里 key 是字典序——那是之前点过「排序」的结果，「转义」本身不重排任何内容。
